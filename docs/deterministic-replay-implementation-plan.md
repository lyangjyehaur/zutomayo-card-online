## Objective

Adopt the external project's strongest reliability practices without copying its Discord-specific architecture. The completed delivery makes every rules-layer random choice part of persisted match state, records a versioned replay manifest and accepted decision trace, reconstructs matches with first-divergence detection, gates effect dispatch coverage, and exposes authorized completed-match replay summaries.

This plan is the tracking source of truth. An item is `Done` only when its implementation, tests, and acceptance evidence are all linked below.

## Evidence And Decisions

The external evidence is pinned to commit `48ba0f9`:

- Its [README](https://github.com/mayonaka-strawberry/zutoka-discord-bot/blob/48ba0f9cee4eae6ffa4ff783f4db5bd635e0c20b/README.md) defines a per-session seeded RNG, a manifest with seed and pre-shuffle decks, an append-only decision log, restart replay, and full replay summaries.

- Its committed [effect dispatch report](https://github.com/mayonaka-strawberry/zutoka-discord-bot/blob/48ba0f9cee4eae6ffa4ff783f4db5bd635e0c20b/tests/baselines/engine/coverage.json) records 232 of 247 registered effects dispatched end to end. Its one-command gate requires 99% line coverage for effect handlers.
- It also implements BO3/BO5 with side decks, Draft, gacha, and PyTorch checkpoints. Those are product expansions, not prerequisites for trustworthy replay.

## Current Delivery

This branch implements `DR-01` through `DR-08` (all complete):

1. Add a stable RNG contract whose `{ algorithm, seed, counter }` state is JSON-serializable.
2. Derive separate setup-only streams for random deck composition, then use the persisted match stream for both deck shuffles and every later random rule choice. This keeps a manifest containing final pre-shuffle deck IDs sufficient for reconstruction.
3. Replace process-global instance allocation on match setup with deterministic per-player IDs.
4. Rebuild both opening decks from the manifest whenever an online deck reservation is bound before the first move, so provisional lobby decks do not alter the final RNG stream.
5. Record all 12 registered boardgame moves only after the underlying rules function accepts them, preserving caller, canonical arguments, request fingerprint, sequence, and post-state fingerprint.
6. Reconstruct matches from manifest schema v1 through the same `GameLogic` functions and stop at the first unsupported manifest, rules-version mismatch, sequence gap, request mismatch, invalid decision, or post-state mismatch.
7. Exclude only wall-clock and presentation fields from FNV-1a 64-bit replay fingerprints; deterministic rules state, pending interactions, RNG, and manifest remain covered.
8. Redact RNG state, replay manifest, decision trace, and replay status from `playerView`; the server remains authoritative.
9. Serialize valid replays as canonical JSONL containing one manifest line, ordered decision lines, and one complete deterministic final-state line.
10. Commit a three-scenario golden matrix covering mulligan RNG, timeout RNG, and a complete match; normal tests are read-only and baseline changes require the explicit update command.
11. Dispatch every parsed production effect through the executor's central handler boundary, report action and choice coverage, and require 100% in the release card dataset gate.
12. Persist a bounded schema-v1 replay summary only after an authoritative match completes, then expose it only to either participant through match history search and replay details.

Out of scope for this delivery: backfilling legacy match summaries, public/spectator replay access, new competitive formats, and AI training changes.

### DR-04 Delivery

The completed second delivery records every accepted boardgame move as a server-only decision record containing a schema version, monotonic sequence, acting player, move name, canonical arguments, a pre-move request fingerprint, and a post-move deterministic state fingerprint. Invalid attempts do not append records.

Replay starts from manifest schema v1 and applies decisions through the same `GameLogic` functions. It rejects unsupported rules versions, sequence gaps, request mismatches, invalid decisions, and post-state mismatches at the first divergent record. Timeout replay may satisfy the elapsed-time precondition, but it still executes the normal timeout rule path and all other legality checks. Decision traces and replay status are redacted from live player views.

Decision replay remains the authority for accepting or rejecting a trace; transcript generation only succeeds after a complete replay verifies every decision.

### DR-05 And DR-06 Delivery

Transcript schema v1 is newline-delimited canonical JSON: a manifest header, one line per accepted decision, and a deterministic final-state footer. Each line is independently parseable, object keys are sorted recursively, and the file ends with one newline. The footer deliberately includes complete server rules state for useful diffs while excluding `actionLog`, UI notices, wall-clock fields, the trace itself, and replay status.

The committed golden matrix uses isolated effect-free fixture cards so it does not depend on mutable production card sources. It covers an opening with mulligan shuffle, a timeout-generated janken choice, and a complete 56-decision match. `replayTranscript.test.ts` regenerates all three in memory and compares them byte for byte; it never writes files. Intended rule changes update baselines only through `npm run replay:goldens:update`, making transcript churn explicit in review.

### DR-07 Delivery

`effect-dispatch-coverage.ts` loads the selected authoritative card source, reports original effect-line count and every runtime effect produced by parser expansion, and sends each runtime effect through the same `executeEffect` action and `requestChoice` dispatchers used in matches. Conditions are removed only in this diagnostic harness so every registered handler is reached; action parameters and choice types remain unchanged. The report contains deterministic card/effect IDs, per-action and per-choice buckets, and exact missing entries. The threshold is 100%, and `evaluateCardDataset` makes it part of the release card dataset gate so the check runs against the actual release snapshot rather than a committed copy of restricted card data.

### DR-08 Delivery

Migration `000049_match_replay_summaries` adds a nullable JSONB summary to completed match records. Match submission derives schema v1 summaries from verified server-owned boardgame state and the sanitized action log. Summaries contain the result, phase spans, ordered decisions, effect order, explicitly revealed hand card definitions, and the sanitized timeline. They deliberately omit raw player state, unrevealed hands, decks, RNG state, and replay manifests.

`GET /api/matches/:id/replay` uses the same participant predicate as the action-log endpoint; a non-participant receives `403`, and a legacy row without a summary receives `404`. Match lists expose only availability plus a bounded search index. The history page searches result, phase, move, effect, choice, and card tokens, filters by outcome, and lazily fetches full replay details for the selected match.

## Compatibility And Rollout

- Newly created matches carry replay schema v1. Persisted legacy states without RNG metadata remain playable through a deterministic compatibility initializer, but they cannot claim a complete replay manifest.
- The RNG algorithm identifier is immutable. Any future algorithm change requires a new identifier and replay support for both versions.
- `rulesVersion` remains the compatibility boundary for rules and card data. Replay consumers must reject unsupported rule versions rather than silently using current behavior.
- Seeds and pre-shuffle decks are server-only during active play because exposing either can reveal future random outcomes or hidden deck composition.
- Decision traces are complete only for matches created after DR-04. Legacy matches without a trace remain playable but cannot be certified by `replayMatch`.
- Transcript schema v1 and every golden fixture are rules-version bound. A deliberate rule/version change must regenerate and review affected JSONL baselines in the same change.
- Replay summaries are written only for newly submitted completed authoritative matches after migration `000049`; legacy history remains readable through the existing sanitized action-log endpoint.
- Replay endpoints require authenticated match participation. Search indexes and summaries are never returned from public, spectator, or live-match APIs.
